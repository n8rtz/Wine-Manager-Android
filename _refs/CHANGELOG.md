- **The Lab's producer/linked-wine resolvers get their own time budget, and the cached index is no longer re-hashed on every open.** The ~30 % of labels whose **Resolver completed within budget** row was blocked were not abstentions: one 500 ms slice covered *both* `ProducerGazetteer.open` — which re-read and SHA-256'd the 10.7 + 23.0 MiB (or 26.6 + 23.0 MiB expanded) cached copies on every photo, twice per photo across the two contenders — *and* the producer plus linked-wine lookups, which were then handed only the leftovers. Setup and lookups now have separate budgets (`TextLabBudgets.GAZETTEER_SETUP_MS` = 800 ms, then `GAZETTEER_LOOKUP_MS` = 2000 ms measured from the end of setup), and `ProducerGazetteer.load` proves a cached copy with a stamped hash + byte length written after the atomic move instead of re-hashing 34–50 MB; the manifest record counts are still checked against the opened database on every open, and a cache miss, length change or missing stamp falls back to the full copy-and-verify path. Measured basis: one fuzzy producer lookup costs ~11 ms (short keys) to ~30 ms (long keys) of SQLite work on a desktop CPU and a linked-wine lookup ~35 ms, against up to 128 eligible spans per label, so the old leftover-of-500 ms window was routinely exhausted; a blocked row is a lost producer/wine suggestion, never a disagreement. The funnel definition is unchanged — returning normally, including abstention, still passes. `tools/tests/test_resolver_budget.py` pins both fixes; device timing still pending.
- **Lab v4 can now try one engine reading for producer and linked wine — off by default.** `ProducerResolver` and `LinkedWineResolver` required two OCR engines with disjoint observations before an identity could become a suggestion, which is the same quorum the appellation repair just dropped: ML Kit is markedly weaker than Paddle on script faces, so a name only Paddle read never reached the filter. New `ProducerResolver.Policy` (`prod` = two engines, the default; `singleReading` = one engine) is threaded through `LinkedWineResolver` so all three independence checks follow it — the producer group filter, the exact validation of an already-present producer, and the wine group filter — while eligibility, edit distance, the single-identity rule, separation from a rival within one edit, the producer/wine observation split and existing-value protection are untouched, so the measured delta is the quorum alone. Only the **Lab v4** contender can use it: `TextLabWineExtraction` builds `Policy.singleReading` only when `expanded && singleReading`, and the **Prod v3.0** contender keeps the Prod rule, so a run still compares the two policies rather than two builds. The switch is `PhoneCorpusRunner.SINGLE_READING_RESOLVERS_IN_BENCHMARK` (false), exported per CSV as `resolver_single_reading_enabled`; flipping it needs **New Lab run** so one corpus never mixes settings. The OCR Labs screen gains an **Accept one engine reading for producer and linked wine (experimental)** checkbox. ## [Structural: Data Normalization & Naming] - 3/15/2026
* **Symptom:** Prices not showing up for specific wines in rankings even though they existed in the cellar under "Kirkland Signature".
* **Cause:** Duplicate `WineDefinition` entries caused by slight naming inconsistencies (e.g., "Kirkland" vs. "Kirkland Signature"). Tasting notes were linked to one ID, while bottles were linked to the other, creating a siloed data structure.
* **Fix:** Implemented `MIGRATION_10_11` to merge duplicate definitions and reassign all child records (bottles, notes, ratings) to a single standardized ID.
* **Key Takeaway:** Fuzzy matching (like `LIKE` queries) is a good temporary bandage for UI, but **structural data normalization** via migrations is the only permanent fix for relational integrity. Always look for "Duplicate Definition" patterns when data seems to be missing across screens.
