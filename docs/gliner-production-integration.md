# GLiNER in Add Wine

The existing Add Wine camera and photo picker both use the same local GLiNER workflow as the GLiNER lab: decoded photo -> ML Kit and PP-OCRv6 readings -> fusion for the INT4 model -> Lab v7 integrated spatial extraction on the original readings -> GLiNER v10 field-decision policy. It uses the lab's default three prompts and integrated modules; benchmark targets are never provided. Existing Lab v7 and legacy scanner benchmark paths remain separate. There is no separate production button, switch, or model-specific message in the regular review UI.

The exact tested GLiNER-Small INT4 graph, tokenizer and config are included in this repository under `app/src/main/assets/gliner-lab-v1`. The graph and tokenizer are gzip-compressed; the graph is split into two files under 90 MB each. Ordinary builds include the assets automatically, without Git LFS, a GLiNER download, or an opt-in build flag. On first use the app reconstructs them into app-private storage, checks their pinned sizes and SHA-256 hashes, and requires the INT4 graph before scanning. A failed installation never replaces an existing file with a partial copy. This initial installation needs space for the approximately 131 MB unpacked graph and can add latency to the first scan. Other pre-existing build dependencies, including PP-OCRv6 provisioning, are unaffected.

A missing, invalid or non-INT4 bundle, model failure or timeout is reported as a generic scan failure with retake/manual entry; it is **not silently replaced with a different scanner**. Detailed diagnostics identify the actual pipeline and failure. No model, label photo, or wine lookup is downloaded/uploaded at scan time.

The GLiNER lab reads the whole decoded photo without the legacy scanner's label-quad localization or quality gate. The adapter retains the workflow's GREEN/YELLOW/RED states internally, but Add Wine does not show the lab's colored review section or require individual confirmations. Supported values fill ordinary editable form fields; missing values stay blank and existing manual edits remain protected by `ScanFormState`. When either OCR engine produces no readings, GREEN fields are downgraded internally. The historical 148/188 phone benchmark is not a measurement of performance on live camera scenes.

The overall scan budget is 90 seconds from capture/import, including model initialization, OCR and field extraction. Native calls are cooperative: cancellation waits for native cleanup, and the existing shared scan/native gate prevents overlapping bitmap work. Model and run-scoped database handles close in `finally`; the caller owns and deletes the temporary input photo.

Tests cover result conversion, protected edits, failure routing, shared camera/picker routing and offline dependency boundaries. Full on-device OCR, quality on uncropped scenes, cold-start latency and memory use require a real Android test; the saved-OCR development benchmark is not an end-to-end Add Wine benchmark.


## Background scan and draft

A user-initiated scan is owned by a process-scoped session and a foreground service with a bounded partial wake lock. Leaving the screen, switching apps or locking the device does not cancel a scan already reading a photo; an unfinished shutter can still be cancelled if the camera is stopped. Android displays a foreground-service notification (subject to notification permission settings). A completed result is stored privately before the temporary photo is deleted and is applied to a saved Add Wine draft on return. The wine is added to the cellar only when the user taps Save, and the draft is cleared only after the database save succeeds. The scan stores a recovery record for a copied photo so a system-recreated service can retry it after process eviction; Android force-stop, device reboot, lost picker access before the copy, storage failure and aggressive manufacturer restrictions can still interrupt work. Full background, lock-screen, recovery and notification behavior requires real-device testing.
