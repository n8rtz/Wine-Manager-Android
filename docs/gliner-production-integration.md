# GLiNER in Add Wine

Camera and photo-picker scans now try the same local GLiNER workflow as the GLiNER lab: full decoded photo -> ML Kit and PP-OCRv6 readings -> conservative fusion for the INT4 model -> Lab v7 integrated spatial extraction on the original readings -> GLiNER v10 field-decision policy. The production path uses the lab's default three prompts and integrated modules; benchmark targets are not provided. Existing Lab v7 and legacy scanner benchmark paths remain separate.

The graph, tokenizer and config must already be installed through **Settings > Scanner testing > GLiNER lane lab > Import model files**, or be provisioned as the existing opt-in build assets. This repository does not contain the 131 MB model and normal builds do not fetch it. Installed app-private files survive an ordinary app update, but a clean install needs the files again. The production scanner verifies that the bundle is ready and INT4 before opening it. It does not download photos or model data during a scan. If the bundle is missing, rejected, or a GLiNER stage fails/times out, Add Wine explicitly reports that it used the previous offline scanner; if both fail, it shows a retake/manual-entry message.

The GLiNER lab reads the entire decoded photo, without the old scanner's label-quad localization or its image-quality gate. To avoid treating this less-restricted input as validated, every populated GLiNER suggestion is **YELLOW**, requiring confirmation; blank or RED/unknown fields remain empty. Existing user edits remain protected by `ScanFormState`. There is no claim that the historical 148/188 phone benchmark predicts performance on camera scenes. Hold the label close and review every field.

The Add Wine overall scan budget is 90 seconds from capture/import, including model initialization, with 15 seconds reserved for a fallback attempt. The legacy fallback still uses its own 15-second bound. Native calls are cooperative: cancellation waits for native cleanup, and the existing shared scan/native gate prevents overlapping bitmap work. Model and run-scoped database handles close in `finally`; the caller owns and deletes the temporary input photo. Scan diagnostics identify the active pipeline, model status, OCR counts, stages and budget without storing the photo path.

Tests cover result conversion, protected edits, route selection/cancellation, shared camera/picker routing and offline dependency boundaries. Full on-device OCR, quality on uncropped scenes, cold-start latency and memory use still require a real Android test; the saved-OCR development benchmark is not an end-to-end Add Wine benchmark.
